# A public `/index.json` route is the second Live evidence surface

Live requires two independent facts to match, never merge or build success: the public article page's content fingerprint, and the site's separate build-time index metadata (spec; CONTEXT.md `Live`). The article page's `<meta name="jelementi-content-version">` already proves the first fact — it is a SHA-256 of the *entire* `ArticleDocument`, so a matching fingerprint cryptographically proves every document field rendered correctly. It proves nothing about the second, genuinely independent fact: that the article's entry is correctly present in `generated/index.json`, the separate artifact that drives the homepage, `/search`, and category pages, which could diverge from the article page's own render on a build or generation bug even when the article page itself is perfect.

Neither existing reader page exposes enough structured, scrapable data to reconstruct the full set of index fields (tags, author, cover, dates are not all rendered as visible text), and `/search`'s hydration payload is SvelteKit-internal serialization, not a stable public contract — parsing it would couple probes to SvelteKit's internals. The decision is to add `apps/web/src/routes/index.json/+server.ts`, a prerendered, non-hydrated `GET` endpoint serving `generatedContent.index` (the same data already bundled into the homepage and search routes) minus `searchText`, as `application/json` with an `X-Robots-Tag: noindex` header (the JSON equivalent of `app.html`'s `<meta name="robots" content="noindex">`, which only applies to HTML responses). This is additive-only: it does not change any existing reader route's `prerender`/`csr` flags, and JSON output has no hydration concept. It also gives T6 (Unpublish, #18) a ready-made way to prove absence from the public index for free.
